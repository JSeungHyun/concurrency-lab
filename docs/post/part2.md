# 동시성 테스트 (레디스, 비관적 & 낙관적 LOCK 등) 2편: 재고가 충분할 때와 재고 분할

## 1편에서 남은 의문

1편에서는 쿠폰 100장에 요청 수천 건이 몰리는 매진 상황을 테스트했고, Redis Lua 스크립트가 가장 빨랐다. 그런데 그 조건은 요청 대부분이 매진으로 거절되기 때문에, 측정한 것은 쓰기 성능보다 매진을 얼마나 빨리 응답하느냐에 가까웠다.

그래서 이번에는 쿠폰 수량을 요청 수와 같게 늘려서 모든 요청이 실제 발급까지 가도록 했다. 재고가 넉넉한 이벤트나, 오픈 직후 아직 재고가 남아 있는 구간에 해당하는 상황이다. 이 조건에서도 Redis 가 가장 빠를 거라고 예상했다.

**1. 락 방식에 상관없이 처리량이 비슷했다**

조건부 UPDATE, 비관적 락, synchronized, Redisson, Redis Lua 의 처리량이 모두 초당 74~82건 범위였다. 방법 간 차이는 ±6% 이내다. 1편에서 초당 2,880건이던 Redis Lua 도 82건으로 내려왔다.

이유는 모든 요청이 쿠폰 행 하나의 발급 수량을 1씩 올려야 하기 때문이다. 한 행은 한 번에 한 트랜잭션만 수정할 수 있어서, 락을 JVM 에 두든 DB 에 두든 Redis 에 두든 결국 그 행 앞에서 순서를 기다리게 된다. 이렇게 쓰기가 한 행에 몰리는 것을 hot row 라고 한다. 이 조건에서는 락 방식보다 hot row 가 처리량을 결정했다.

**2. 재고 분할만 처리량이 높았다**

재고 분할은 초당 277건으로 다른 방법의 3.4배였다. 뒤에서 자세히 다룬다.

**4. 처리량이 같아도 응답 시간은 달랐다**

처리량이 비슷한 방법들 사이에서도 p99 는 차이가 났다. 조건부 UPDATE 가 약 3.6초로 가장 짧았고 synchronized 가 약 5.9초로 가장 길었다. synchronized 는 트랜잭션 전체를 락 하나로 순서대로 처리해서 대기 시간이 그대로 응답 시간에 더해진다.

참고로 제어가 없는 경우는 초과 발급은 없었지만 쿠폰 테이블의 발급 수량 컬럼이 실제보다 2,850건 적게 기록됐다. 수량을 넘기지 않았다고 해서 데이터가 맞는 것은 아니었다.

## Redis Lua 도 같아진 이유

Redis 를 쓰면 더 빠를 거라고 예상했기 때문에 이 결과가 가장 의외였다. 구현을 다시 보니 이유는 단순했다. Redis 에서 예약에 성공한 요청은 그 자리에서 DB 에 기록한다. 매진 상황에서는 대부분의 요청이 Redis 에서 끝나지만, 재고가 충분하면 모든 요청이 DB 쓰기까지 가야 하고 그 쓰기는 다른 방법과 똑같이 쿠폰 행 하나에 몰린다.

발급과 거절이 섞인 조건에서도 확인해 봤다. 쿠폰 1,000장에 요청 10,000건, 동시 500명이다.

{{MEDIAN:partial}}

Redis Lua 는 처리량은 2위였지만 p99 가 4.8초로 조건부 UPDATE(3.5초)보다 길었다. 거절은 빠르게 처리해도 발급에 성공한 1,000건이 DB 에서 밀리기 때문이다.

정리하면 Redis 가 빠른 것은 DB 에 가지 않아도 되는 요청을 걸러 낼 때다. DB 에 써야 하는 요청이 많아지면 그 이점이 줄어든다. 실무에서는 Redis 에서 판정만 하고 DB 기록은 큐에 넣어 나중에 처리하는 방식을 쓴다고 하는데, 이번에는 테스트하지 못했다.

## 재고 분할

hot row 가 병목이라면 락을 바꾸는 것으로는 해결되지 않는다. 그래서 수정할 행 자체를 여러 개로 늘려 봤다.

재고 100장을 행 하나에 100으로 저장하지 않고 10장짜리 슬롯 10개 행으로 나눠서 저장한다. 요청이 들어오면 재고가 남은 슬롯 중 하나를 무작위로 골라 그 행에만 조건부 UPDATE 를 실행한다.

```java
// 남은 슬롯 중 하나를 임의로 골라 시도하고, 비었으면 다음 슬롯으로 넘어간다
List<Long> candidates = stockRepository.findAvailableIds(couponId);     // 잠금 없는 스냅샷 읽기
int start = ThreadLocalRandom.current().nextInt(candidates.size());
for (int i = 0; i < candidates.size(); i++) {
    long slotId = candidates.get((start + i) % candidates.size());
    if (writer.issueFromSlot(couponId, slotId, userId)) return;         // 시도마다 새 트랜잭션
}
throw new IssueException(SOLD_OUT);                                     // 모든 슬롯이 비면 매진
```

```sql
-- issueFromSlot 안에서 도는 조건부 UPDATE. 슬롯 하나에만 건다.
UPDATE coupon_stock SET issued_quantity = issued_quantity + 1
WHERE id = ? AND issued_quantity < total_quantity
```

### 구현 중 발생한 데드락

처음에는 트랜잭션 하나 안에서 슬롯을 차례로 시도하도록 구현했다. 이 상태로 부하를 걸자 MySQL 이 데드락(에러 1213)을 감지해 요청 일부를 롤백했다.

원인은 조건에 맞지 않아 0건을 수정한 UPDATE 도 해당 행의 잠금을 트랜잭션이 끝날 때까지 유지한다는 점이었다. 요청 A 가 슬롯 1의 잠금을 가진 채 슬롯 2를 시도하고, 요청 B 가 슬롯 2의 잠금을 가진 채 슬롯 1을 시도하면 서로 상대의 잠금을 기다리게 된다.

슬롯을 시도할 때마다 트랜잭션을 새로 시작하도록 바꿔서 해결했다. 위 코드에서 `issueFromSlot` 에 `@Transactional` 을 붙인 것도 이 때문이다. 트랜잭션 하나가 잠그는 슬롯이 최대 1개이므로 데드락이 생기지 않고, 수정한 뒤로는 재현되지 않았다.

## 정리: 상황별 선택 기준

두 편의 결과를 합치면, 어떤 상황에서나 가장 빠른 방법은 없었다. 아래 두 가지에 따라 적합한 방법이 달라졌다.

**거절되는 요청과 발급되는 요청 중 어느 쪽이 많은가**

- 매진으로 거절되는 요청이 훨씬 많은 경우(인기 상품 오픈): Redis Lua 가 가장 빠르고 부하가 클수록 차이가 커진다. Redis 를 쓸 수 없다면 재고 분할이 그다음이다.
- 대부분의 요청이 실제 발급까지 가는 경우: 어떤 락을 써도 쓰기가 한 행에 몰려서 처리량이 비슷하다. 그 정도로 충분하면 조건부 UPDATE, 더 필요하면 재고 분할로 행을 나눠야 한다.

**서버가 1대인가 여러 대인가**

- 1대: synchronized 도 가능하지만 조건부 UPDATE 가 코드도 간단하고 응답 시간도 짧았다.
- 여러 대: synchronized 는 쓸 수 없다. DB 만 쓴다면 조건부 UPDATE, Redis 를 쓸 수 있고 매진 요청이 많다면 Redis Lua 가 적합하다.

| 방법 | 매진 RPS (3,000건) | 매진 RPS (30,000건) | 재고 충분 RPS | 서버 여러 대 | 특징 |
|---|---|---|---|---|---|
| synchronized | 1,017 | 1,267 | 77 | ✗ | 서버 1대에서만 유효 |
| 비관적 락 | 982 | 2,148 | 79 | ○ | 안전하지만 대기 중에도 커넥션 사용 |
| 낙관적 락 | 1,413 | 2,944 | 46 | ○ | 쓰기 충돌이 많으면 재시도 급증 |
| 조건부 UPDATE | 1,434 | 2,138 | 82 | ○ | DB 만 쓸 때 기본 선택. 코드가 간단 |
| Redisson 분산 락 | 684 | 841 | 74 | ○ | 처리량 이점 없음. 분산 락 자체가 필요할 때 사용 |
| Redis Lua | 2,880 | 8,187 | 82 | ○ | 매진 요청이 많을 때 가장 빠름. Redis 와 DB 불일치 처리 필요 |
| 재고 분할 | 2,948 | 4,216 | 277 | ○ | 재고가 충분할 때 유일하게 처리량이 높음. 슬롯 수 조정 필요 |

## 배운 점

수습 과제 때는 동시성 문제에 Redis 를 쓰면 된다고만 알고 있었다. 직접 비교해 보니 Redis 는 DB 로 가는 요청을 줄여 줄 때 효과가 크고, 결국 DB 에 써야 하는 요청이 많은 상황에서는 다른 방법과 차이가 없었다. 같은 Redis 라도 분산 락과 Lua 스크립트는 결과가 반대였다.

또 하나는 락을 고르는 것과 처리량을 높이는 것이 다른 문제라는 점이다. 락은 정합성을 지키기 위한 것이고, 쓰기가 한 행에 몰리는 구조에서는 어떤 락을 써도 처리량이 같았다. 처리량을 높인 것은 데이터 구조를 바꾼 재고 분할이었다.

## 한계

- PC 한 대에서 k6 와 앱이 CPU 를 같이 사용했다. 수치 자체보다는 방법 간의 상대적인 차이를 참고하는 것이 좋다.
- 서버 1대로만 테스트했다. synchronized 가 서버 여러 대에서 깨지는 것과 분산 락의 이점은 직접 확인하지 못했다.
- 조건마다 3회씩만 측정했다. 처리량이 비슷한 방법들 사이의 작은 순위 차이는 판단하기 어렵다.
- 커넥션 풀 대기 시간, MySQL 잠금 대기 시간 같은 서버 내부 지표는 수집하지 않았다. 병목 원인은 구조와 응답 시간 분포로 추정한 것이다.
- 재고 분할의 슬롯 수 10개는 이번 부하 조건에 맞춘 값이다.

## 추가로 해 볼 것

- Redis 에서 판정하고 DB 기록은 큐로 비동기 처리했을 때 재고 충분 조건의 처리량
- 서버 2대와 로드밸런서 구성에서 synchronized 가 깨지는 것과 분산 락의 효과 확인
- Prometheus 로 커넥션 풀 대기, 잠금 대기 같은 서버 내부 지표를 수집해서 병목을 수치로 확인
- Redis 와 DB 기록 사이에 앱이 종료됐을 때 불일치한 데이터를 복구하는 방법
