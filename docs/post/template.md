# 동시성 테스트 (레디스, 비관적 & 낙관적 LOCK 등)

## 개요

선착순 쿠폰 발급은 "남은 수량을 확인하고 남아 있으면 한 장 발급한다"는 간단한 기능이다. 요청이 한 번에 하나씩 들어올 때는 문제가 없지만, 오픈 직후처럼 수천 명이 동시에 요청하면 수량보다 많이 발급되는 문제가 생긴다.

이 글은 쿠폰 발급 API 하나를 두고 동시성 제어 방법을 바꿔 가며 같은 부하를 걸어 본 기록이다. 아무 제어가 없는 상태에서 시작해 synchronized, 비관적 락, 낙관적 락, 조건부 UPDATE, Redisson 분산 락, Redis Lua 스크립트를 차례로 적용했고, 마지막으로 재고를 여러 행으로 나누는 방법(재고 분할)까지 테스트했다. 방법마다 정합성이 지켜지는지와 처리량, 응답 시간이 어떻게 달라지는지를 k6 와 Grafana 로 측정했다.

## 결론 요약

- 정합성은 어떤 방법이든 하나만 적용하면 지켜졌다. 깨진 것은 제어가 없을 때뿐이다. 단, synchronized 는 서버가 1대일 때만 유효하다.
- 매진으로 거절되는 요청이 대부분인 상황에서는 Redis Lua 와 재고 분할이 DB 락 방식보다 2~3배 빨랐다.
- 재고가 충분해서 모든 요청이 실제 발급까지 가는 상황에서는 어떤 락을 쓰든 처리량이 초당 74~82건으로 비슷했다. 쿠폰 행 하나에 쓰기가 몰리는 것이 병목이었고, 재고를 10개 행으로 나누자 처리량이 3.4배로 늘었다.
- 낙관적 락은 경합이 심한 선착순에는 맞지 않았다. 처리량이 가장 낮았고, 응답이 18초까지 늘어났으며, 재고가 남았는데도 발급받지 못한 요청이 생겼다.

## 테스트 환경

```
 k6 (부하 발생) ──▶ Spring Boot 앱 ──▶ MySQL 8.4
      │                   └─────────▶ Redis 7.4
      ▼
 InfluxDB ──▶ Grafana
```

- 전부 Docker Compose 로 PC 한 대에서 실행했다. 앱 컨테이너는 CPU 2코어, 메모리 1GB 로 제한했고 DB 커넥션 풀은 20, Tomcat 스레드는 200 으로 고정했다.
- 실행할 때마다 쿠폰을 새로 만들고, 요청마다 서로 다른 사용자 ID 를 사용했다.
- 측정 전에 JVM 워밍업을 한 번 돌렸고 이 결과는 기록하지 않았다.
- 조건마다 3번씩 반복했다. 글에 나오는 수치는 모두 3회 중앙값이고, 그래프는 1회차를 Grafana 에서 캡처한 것이다.

### 테스트 시나리오

같은 방법이라도 재고가 얼마나 남아 있는지에 따라 결과가 크게 달라져서 시나리오를 두 개로 나눴다.

| 시나리오 | 조건 | 특징 | 실제 사례 |
|---|---|---|---|
| 재고 부족 | {{CONDITIONS:burst}} | 요청 대부분이 매진으로 거절된다 | 인기 쿠폰 오픈처럼 재고보다 사람이 훨씬 많을 때 |
| 재고 충분 | {{CONDITIONS:write}} | 거의 모든 요청이 실제 발급(DB 쓰기)까지 간다 | 재고가 넉넉한 이벤트, 또는 오픈 직후 재고가 남아 있는 구간 |

방법별 설명은 재고 부족 시나리오의 결과를 기준으로 하고, 재고 충분 시나리오는 뒤에서 따로 비교한다.

### 주요 관찰 포인트

| 지표 | 의미 | 정상 |
|---|---|---|
| 초과 발급 | 실제 발급 행 수 − 쿠폰 수량 | 0 |
| 갱신 손실 | 실제 발급 행 수 − 쿠폰 테이블의 발급 수량 컬럼 | 0 |
| RPS | 초당 처리한 발급 요청 수 | 높을수록 좋음 |
| p50 / p99 | 응답 시간을 빠른 순으로 정렬했을 때 50% / 99% 지점 | 낮을수록 좋음 |

가장 먼저 보는 것은 정합성이다. 처리량이 아무리 높아도 초과 발급이 1건이라도 나오면 그 방법은 실패로 본다.

### 정합성 사전 검증

부하테스트는 시간이 오래 걸리고 실행할 때마다 결과가 조금씩 달라진다. 그래서 정합성은 JUnit 테스트로 먼저 확인했다. 실제 MySQL, Redis 컨테이너에 스레드 64개로 동시에 요청을 보내고 결과를 검사하는 테스트다.

| 테스트 | 조건 | 기대 결과 |
|---|---|---|
| 재고 부족 | 50장에 300명 | 정확히 50장 발급, 매진 외 실패 0건 |
| 재고 충분 | 200장에 200명 | 전원 발급 |
| 중복 요청 | 같은 사용자가 동시에 20번 요청 | 1장만 발급, 롤백된 요청이 발급 수량을 올리지 않음 |
| 대조군 | 제어 없음, 50장에 300명 | 정합성이 깨져야 함 |

방법 7개에 테스트 3종을 적용하고, 대조군과 재고 분할 경계값(슬롯 수보다 적은 7장) 테스트를 더해 총 24개다. 3번 실행해서 모두 통과했다. 대조군은 테스트가 실제로 경합을 만들어 내는지 확인하려고 넣었다. 경합이 생기지 않는 테스트라면 어떤 방법이든 통과하기 때문이다.

## 0. 제어 없음

```java
@Transactional
public void issue(long couponId, long userId) {
    Coupon coupon = couponRepository.findById(couponId).orElseThrow();   // ① 읽고
    if (coupon.getIssuedQuantity() >= coupon.getTotalQuantity()) {       // ② 검사하고
        throw new IssueException(SOLD_OUT);
    }
    couponRepository.overwriteIssuedQuantity(couponId, coupon.getIssuedQuantity() + 1);  // ③ 쓴다
    issueRepository.save(new CouponIssue(couponId, userId));
}
```

{{IMG:burst:compare-issued}}

100장짜리 쿠폰이 2,000장 발급됐다. 그런데 쿠폰 테이블의 발급 수량 컬럼은 100으로 기록되어 있어서 이 컬럼만 보면 정상으로 보인다. 발급 기록 테이블의 행 수를 직접 세어 봐야 초과 발급을 알 수 있다.

원인은 ① 읽기와 ③ 쓰기 사이에 다른 요청이 끼어들 수 있다는 점이다. 두 요청이 거의 동시에 들어오면 다음과 같이 처리된다.

```
요청 A: ① 50 읽음 ─ ② 통과 ─ ③ 51 저장 ─ INSERT
요청 B:   ① 50 읽음 ─ ② 통과 ─ ③ 51 저장 ─ INSERT
```

쿠폰은 2장 발급됐는데 컬럼 값은 51이 된다. MySQL(InnoDB)의 일반 `SELECT` 는 잠금 없이 스냅샷을 읽기 때문에 다른 트랜잭션이 같은 행을 수정하고 있어도 기다리지 않고 이전 값을 읽는다.

{{IMG:burst:naive-status}}

응답 상태를 초 단위로 보면 처음에는 발급 성공(200)만 계속 나오고 매진(409)은 마지막에 몰려서 나온다. 매진 판정이 늦어지는 만큼 거의 모든 요청이 INSERT 까지 실행되기 때문에 처리 속도도 전체 방법 중 가장 느렸다.

뒤에 나오는 방법들은 모두 이 문제를 막기 위한 것이다. 읽기와 쓰기 사이에 다른 요청이 끼어들지 못하게 하거나, 끼어들었을 때 감지해서 다시 처리하는 방식이다.

## 1. synchronized

```java
@Override
public synchronized void issue(long couponId, long userId) {
    writer.issueReadCheckWrite(couponId, userId);   // 트랜잭션은 락 안에서 시작하고 끝난다
}
```

**결과**: {{RESULT:burst:synchronized}}

한 번에 한 요청만 메서드에 들어갈 수 있어서 정합성이 지켜졌다. 사용할 때 주의할 점이 두 가지 있다.

- `@Transactional` 이 붙은 메서드에 `synchronized` 를 같이 붙이면 안 된다. 락이 풀린 뒤에 프록시가 커밋하기 때문에 그 사이에 다른 요청이 커밋 전 값을 읽을 수 있다. 위 코드처럼 트랜잭션 전체가 락 안에서 시작하고 끝나도록 분리해야 한다.
- 락이 JVM 메모리에 있어서 서버가 2대 이상이면 서버마다 따로 락을 잡게 되고 정합성이 다시 깨진다. 이번 테스트는 서버가 1대라서 통과했다.

## 2. 비관적 락 (SELECT FOR UPDATE)

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select c from Coupon c where c.id = :id")
Optional<Coupon> findByIdForUpdate(@Param("id") Long id);   // SELECT ... FOR UPDATE
```

**결과**: {{RESULT:burst:pessimistic}}

`FOR UPDATE` 로 조회하면 쿠폰 행에 배타 잠금이 걸리고 트랜잭션이 커밋될 때까지 유지된다. 다음 요청은 앞 요청이 커밋한 뒤에야 행을 읽을 수 있어서 항상 최신 값을 보게 된다. 잠금이 DB 에 있으므로 서버가 여러 대여도 동작한다.

단점은 모든 요청이 순서대로 하나씩 처리된다는 것이다. 매진된 뒤에 들어온 요청도 잠금을 잡고 나서야 매진을 확인할 수 있다. 또 잠금을 기다리는 동안에도 DB 커넥션을 계속 쓰고 있어서 요청이 몰리면 커넥션 풀이 금방 부족해진다.

{{IMG:burst:pessimistic-latency}}

## 4. 조건부 UPDATE

```sql
UPDATE coupon SET issued_quantity = issued_quantity + 1
WHERE id = ? AND issued_quantity < total_quantity
```

**결과**: {{RESULT:burst:atomic-update}}

수량 검사와 증가를 SQL 한 문장으로 처리한다. 읽기와 쓰기가 나뉘어 있지 않으므로 그 사이에 다른 요청이 끼어들 수 없다. 변경된 행이 0개면 매진으로 판단한다. 이 UPDATE 도 내부적으로는 행 잠금을 사용하지만, 잠금을 잡은 채로 앱과 DB 를 여러 번 오가지 않아서 잠금 시간이 짧다. 코드도 지금까지 본 방법 중 가장 간단하다.

재고 부족 시나리오에서는 DB 만 사용하는 방법 중 가장 빨랐다(초당 1,434건). 비관적 락(982건)보다 3회 모두 높게 나왔다. 재고 충분 시나리오에서는 다른 방법들과 처리량이 비슷했지만 p99 응답 시간은 가장 짧았다. 이 부분은 뒤에서 다시 다룬다.

## 5. Redisson 분산 락

```java
RLock lock = redisson.getLock("coupon:" + couponId + ":lock");
if (!lock.tryLock(waitMs, TimeUnit.MILLISECONDS)) throw new IssueException(LOCK_TIMEOUT);
try {
    writer.issueReadCheckWrite(couponId, userId);
} finally {
    lock.unlock();
}
```

**결과**: {{RESULT:burst:redisson-lock}}

락을 Redis 에 두기 때문에 서버가 여러 대여도 같은 락을 공유할 수 있다. synchronized 가 서버 1대에서만 동작하는 문제를 해결하는 방법이다. 다만 락을 잡고 풀 때마다 Redis 와 통신해야 하고 그 안에서 DB 작업까지 수행하므로, 서버가 1대인 이번 조건에서는 정합성을 지킨 방법 중 가장 느렸다.

## 6. Redis Lua 스크립트

```lua
local total = redis.call('GET', KEYS[2])
if redis.call('SISMEMBER', KEYS[1], ARGV[1]) == 1 then return -1 end   -- 중복
if redis.call('SCARD', KEYS[1]) >= tonumber(total) then return 0 end    -- 매진
redis.call('SADD', KEYS[1], ARGV[1])
return 1                                                                -- 예약 성공
```

**결과**: {{RESULT:burst:redis-lua}}

Redis 는 명령을 한 번에 하나씩 처리하고, Lua 스크립트는 중간에 다른 명령이 끼어들지 않고 한 번에 실행된다. 이 성질을 이용해 중복 확인, 수량 확인, 예약을 스크립트 하나로 처리하고, 예약에 성공한 요청만 DB 에 기록한다. 매진된 요청은 DB 까지 가지 않고 Redis 에서 바로 거절된다.

{{IMG:burst:redis-lua-latency}}

p50 이 수 ms 수준으로 매우 짧다. 대부분을 차지하는 매진 요청이 DB 를 거치지 않기 때문이다. 대신 데이터가 Redis 와 DB 두 곳에 저장되므로 서로 맞지 않을 수 있다. DB 기록이 실패하면 Redis 예약을 취소하도록 구현했지만, 그 사이에 앱이 종료되면 맞지 않는 상태로 남는다.

## 7. 재고 분할

지금까지의 방법은 모두 쿠폰 행 하나를 안전하게 수정하는 방법이었다. 락을 JVM, DB, Redis 중 어디에 두든 모든 요청은 결국 같은 행 하나를 수정하기 위해 순서를 기다려야 한다. 재고 분할은 락을 바꾸는 대신 수정할 행 자체를 여러 개로 늘리는 방법이다.

재고 100장을 행 하나에 100으로 저장하지 않고 10장짜리 슬롯 10개 행으로 나눠서 저장한다. 요청이 들어오면 재고가 남은 슬롯 중 하나를 무작위로 골라 그 행에만 조건부 UPDATE 를 실행한다. 요청이 10개 행으로 분산되므로 한 행에서 기다리는 요청 수가 줄어든다.

```java
// 남은 슬롯 중 하나를 임의로 골라 시도하고, 비었으면 다음 슬롯으로 넘어간다
List<Long> candidates = stockRepository.findAvailableIds(couponId);     // 잠금 없는 스냅샷 읽기
int start = ThreadLocalRandom.current().nextInt(candidates.size());
for (int i = 0; i < candidates.size(); i++) {
    long slotId = candidates.get((start + i) % candidates.size());
    if (writer.issueFromSlot(couponId, slotId, userId)) return;         // 시도마다 새 트랜잭션
}
throw new IssueException(SOLD_OUT);                                     // 모든 슬롯이 비면 매진
```

```sql
-- issueFromSlot 안에서 도는 조건부 UPDATE. 슬롯 하나에만 건다.
UPDATE coupon_stock SET issued_quantity = issued_quantity + 1
```

### 구현 중 발생한 데드락

처음에는 트랜잭션 하나 안에서 슬롯을 차례로 시도하도록 구현했다. 이 상태로 부하를 걸자 MySQL 이 데드락(에러 1213)을 감지해 요청 일부를 롤백했다.

원인은 조건에 맞지 않아 0건을 수정한 UPDATE 도 해당 행의 잠금을 트랜잭션이 끝날 때까지 유지한다는 점이었다. 요청 A 가 슬롯 1의 잠금을 가진 채 슬롯 2를 시도하고, 요청 B 가 슬롯 2의 잠금을 가진 채 슬롯 1을 시도하면 서로 상대의 잠금을 기다리게 된다.

슬롯을 시도할 때마다 트랜잭션을 새로 시작하도록 바꿔서 해결했다. 위 코드에서 `issueFromSlot` 에 `@Transactional` 을 붙인 것도 이 때문이다. 트랜잭션 하나가 잠그는 슬롯이 최대 1개이므로 데드락이 생기지 않고, 수정한 뒤로는 재현되지 않았다.

## 정리: 상황별 선택 기준

어떤 상황에서나 가장 빠른 방법은 없었다. 아래 두 가지 기준에 따라 적합한 방법이 달라졌다.

### 기준 1. 거절되는 요청과 발급되는 요청 중 어느 쪽이 많은가

- 매진으로 거절되는 요청이 훨씬 많은 경우(인기 쿠폰 오픈): 거절을 쿠폰 행 하나에 몰리지 않게 처리하는 방법이 2~3배 빠르다. Redis 를 사용할 수 있으면 Redis Lua(초당 2,880건), DB 만 사용한다면 재고 분할(초당 2,948건, p99 0.26초)이 적합하다.
- 대부분의 요청이 실제 발급까지 가는 경우(재고가 넉넉한 이벤트): 쿠폰 행 하나에 쓰기가 몰려서 어떤 락을 써도 초당 74~82건 정도가 한계다. 이보다 높은 처리량이 필요하면 재고 분할로 행을 나눠야 한다. 슬롯 10개에서 초당 293건, 50개에서 501건이 나왔다.

### 기준 2. 서버가 1대인가 여러 대인가

- 1대인 경우: synchronized 로도 정합성은 지킬 수 있지만 p99 가 가장 길었다. 같은 조건이라면 코드가 더 간단하고 응답 시간도 짧은 조건부 UPDATE 가 낫다.
- 여러 대인 경우: synchronized 는 사용할 수 없다. DB 만 사용한다면 조건부 UPDATE, Redis 를 사용할 수 있고 매진 요청이 많다면 Redis Lua 가 적합하다. Redisson 분산 락은 처리량 면에서는 이점이 없었으므로, 여러 서버에서 한 번에 하나만 실행되어야 하는 작업처럼 락 자체가 필요한 경우에 사용한다.

## 한계

- PC 한 대에서 k6 와 앱이 CPU 를 같이 사용했다. 수치 자체보다는 방법 간의 상대적인 차이를 참고하는 것이 좋다.
- 서버 1대로만 테스트했다. synchronized 가 서버 여러 대에서 깨지는 것과 분산 락의 이점은 직접 확인하지 못했다.
- 조건마다 3회씩만 측정했다. 재고 충분 시나리오에서 단일 행 방법들의 차이가 ±6% 이내였으므로 처리량이 비슷하다는 결론은 측정 오차 때문이 아니라고 볼 수 있다. 하지만 그 안에서 조건부 UPDATE 와 Redis Lua 중 어느 쪽이 더 빠른지처럼 작은 차이를 판단하기에는 횟수가 부족하다.
- 커넥션 풀 대기 시간, MySQL 잠금 대기 시간 같은 서버 내부 지표는 수집하지 않았다. 병목 원인은 구조와 응답 시간 분포로 추정한 것이고 지표로 직접 확인한 것은 아니다.
- 재고 분할의 슬롯 수 10개는 이번 부하 조건에 맞춘 값이다. 슬롯 수에 따른 변화에서 본 것처럼 적절한 슬롯 수는 트래픽에 따라 달라진다.

## 추가로 해 볼 것

- 서버 2대와 로드밸런서 구성에서 synchronized 가 깨지는 것과 분산 락의 효과 확인
- Prometheus 로 커넥션 풀 대기, 잠금 대기 같은 서버 내부 지표를 수집해서 병목을 수치로 확인
- 재고 분할의 슬롯 수를 트래픽에 따라 조정하는 방법, 발급을 큐로 비동기 처리했을 때의 처리량
- Redis 와 DB 기록 사이에 앱이 종료됐을 때 불일치한 데이터를 복구하는 방법
